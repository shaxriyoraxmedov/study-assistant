# Study Assistant

Учебный ассистент на локальной LLM: отвечает по загруженным конспектам, ищет факты в
Википедии, считает и помнит пользователя между запусками.

Собран как ReAct-агент — модель сама решает, каким инструментом воспользоваться, и её
рассуждения видны в интерфейсе.

## Что внутри

| Возможность | Реализация |
|---|---|
| Ответы по конспектам | RAG: чанкинг → bge-m3 эмбеддинги → Qdrant → cross-encoder reranking |
| Внешние факты | Wikipedia API с fallback на поиск, если прямого совпадения нет |
| Вычисления | `simpleeval` вместо `eval()` — произвольный код не выполняется |
| Долгая память | Факты о пользователе в Qdrant, переживают перезапуск, дедуп по косинусу |
| Защита | Результаты инструментов помечены как данные, санитизация вывода |
| Интерфейс | Streamlit: стриминг ответа, trace рассуждений, память в сайдбаре, светлая/тёмная тема |

## Архитектура

```
                   ┌──────────────┐
    вопрос ───────▶│  Streamlit   │
                   │     UI       │
                   └──────┬───────┘
                          ▼
                  ┌───────────────┐   решает, что вызвать
                  │  ReAct-агент  │◀──────────────┐
                  │  (qwen2.5:7b) │               │
                  └───────┬───────┘               │
                          │ tool call             │ observation
          ┌───────────────┼──────────────┬────────┘
          ▼               ▼              ▼
   ┌────────────┐  ┌────────────┐  ┌───────────┐
   │search_notes│  │ wikipedia  │  │ calculate │
   │  (RAG)     │  │            │  │           │
   └─────┬──────┘  └────────────┘  └───────────┘
         │
         ▼  retrieval top-10 → rerank top-3
   ┌────────────┐        ┌────────────────┐
   │   Qdrant   │        │  долгая память │
   │ rag_notes  │        │  (Qdrant)      │
   └────────────┘        └────────────────┘
```

Ollama работает на хосте, а не в контейнере: модели используют GPU, пробрасывать его
внутрь ради учебного проекта незачем. Приложение ходит к нему через `host.docker.internal`.

## Запуск

Нужны: Docker, [Ollama](https://ollama.com) и вытянутые модели.

```bash
ollama pull qwen2.5:7b
ollama pull bge-m3

docker compose up --build
```

Интерфейс: http://localhost:8501

Конспект (`.txt` / `.md`) загружается через сайдбар — он индексируется в Qdrant, после
чего агент может по нему отвечать. Без конспекта агент работает, но `search_notes`
ничего не находит.

### Локально, без Docker

```bash
python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
docker compose up -d qdrant     # Qdrant всё равно нужен
streamlit run streamlit_app.py
```

## Разработка

```bash
pip install -r requirements-dev.txt
pytest -q          # 31 тест, не требуют Qdrant и Ollama
ruff check .
```

Тестами покрыты чистые функции и защита — безопасность `calculate`, санитизация вывода,
изоляция результатов инструментов, чанкинг и сортировка reranking. Ответы модели
не тестируются: они недетерминированы, для их оценки есть отдельный eval-скрипт.

Отдельно — smoke-тесты страницы через `streamlit.testing`: они проверяют, что UI
строится и переживает перерисовку. Это ловит класс ошибок, невидимый линтеру:
страница рендерится один раз, а на втором прогоне оказывается пустой.

## CI/CD

На каждый push и pull request GitHub Actions гоняет линтер, тесты и сборку образа.
После успешных тестов на `main` образ публикуется в GitHub Container Registry —
на PR он собирается, но не выкладывается.

```bash
docker pull ghcr.io/<владелец>/study-assistant:latest
```

Теги: `latest` — текущий `main`, `sha-<хеш>` — конкретный коммит, чтобы откат вёл
на понятную версию, а не на «тот latest, что был вчера».

Отдельного шага деплоя на сервер нет осознанно: приложению нужен Ollama с моделями
(qwen2.5:7b — 4.7 ГБ) и желательно GPU, поэтому «задеплоить на бесплатный хостинг»
здесь не сработало бы. Опубликованный образ разворачивается одной командой на любой
машине с Ollama — это и есть точка доставки.

## Настройки

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `QDRANT_URL` | `http://localhost:6333` | адрес Qdrant |
| `OLLAMA_HOST` | `http://localhost:11434` | адрес Ollama |
| `NUM_GPU_LAYERS` | `28` | сколько слоёв модели выгружать на GPU |

## Технические заметки

**`NUM_GPU_LAYERS=28`, а не все 29.** На RTX 3060 Laptop (6 ГБ) полная выгрузка
qwen2.5:7b роняет llama-server с `0xc0000409` даже при свободной видеопамяти. 28 слоёв
занимают ~4.5 ГБ и оставляют место для bge-m3, поэтому модели не вытесняют друг друга.
`NUM_GPU_LAYERS=0` — всё на CPU: медленно, но работает всегда.

**Reranking не украшение.** На сравнительных вопросах («чем X отличается от Y») голый
векторный поиск приносил оба термина вперемешку, а нужный фрагмент оставался на 5-7
месте. Cross-encoder читает пару (вопрос, чанк) целиком, поэтому top-10 → top-3 заметно
чище — ценой ~1-2 секунд на CPU.

**Факты хранятся полными предложениями.** «Алишер» как отдельный факт почти не находится
семантическим поиском; «Пользователя зовут Алишер» — находится. Порог дедупликации 0.80
подобран замером: перефразировки одного факта дают 0.86-0.90, разные факты — 0.65-0.71.

**Точка входа вызывает `render()`, а не импортирует модуль.** Streamlit перезапускает
скрипт на каждое взаимодействие, а Python при повторном импорте отдаёт модуль из
`sys.modules`, не выполняя код. С `import app.ui` страница рисовалась ровно один раз,
а при любом действии оказывалась пустой — без ошибок и без строчки в логах.
Диагностируется это плохо, поэтому случай закреплён smoke-тестами.

**Известное ограничение.** На узбекской кириллице в сочетании со сравнительными вопросами
7B-модель иногда теряет связность ответа. На русском и латинизированном узбекском работает
надёжно. Проблема в размере модели, а не в pipeline — воспроизводится и без RAG.

## Стек

Python 3.12, Streamlit, Qdrant, Ollama (qwen2.5:7b, bge-m3),
sentence-transformers (bge-reranker-v2-m3), Docker Compose, pytest, ruff, GitHub Actions.
